## 1. Core, configuration and data

The core owns authorization, conversation transitions, retrieval interfaces, schema validation, deterministic business-rule execution, budgets, audit and consent. It contains no tenant-specific identifiers, prices, stock, fees, persona, channel secrets or sales policy. The present `TENANTS` constants, `SYN-*` identifiers, fixture date and one-entry catalogs are accepted synthetic fixtures only. Before a product build these boundaries must be replaced by validated versioned configuration/data, not expanded `if tenant == NHD` branches. Package shared domain logic; deploy each tenant with scoped credentials/worker/storage. Common code does not mean common private data access.

| Versioned tenant configuration | Tenant-owned data | Secret/reference separation |
| --- | --- | --- |
| Opaque tenant ID/status, locale, persona ID/revision, allowed intent/workflow template IDs, capabilities, public site mapping, retention/budget/rate policy, catalog/corpus active revision, channels/pages, hours, staff-routing policy | Product/service records, approved FAQ/policy paragraphs, price/stock snapshots, customer/lead/consent/conversation/message/ticket records, approval/audit events, signed source manifests | Channel/provider credentials stored outside config; config contains tenant-scoped secret references only. Worker cannot read another tenant's secret. Never place tokens in public config, prompts or GitHub |

Configuration promotion needs schema checks, exact revision/hash approval, a separate authorized reviewer and atomic activation. Business admin can edit only its tenant's business config; cannot select arbitrary code, SQL, URL endpoints or widen its platform permissions. Platform super-admin governs tenant lifecycle, subscription/quota ceilings and incident controls; it is a trusted high-privilege role with MFA, audited changes and no invisible routine access to conversations. Tenant admin manages approved content/staff/channel mapping; sales/staff handles permitted inquiries; end customer accesses only their authorized session/resources. Billing/subscription changes remain Owner-reserved; no billing subsystem is implemented.

Onboarding target without redeploy means **adding an already supported template/channel by data/config**, not loading arbitrary executable plugins. A new channel type or business operation requires reviewed adapter/core code and new approval. Invalid config, missing source rights or unknown workflow fails closed without a partly enabled bot.

## 2. Logical domain model, not a physical migration

| Entity | Identity/scope and important relationships |
| --- | --- |

| channels / pages | tenant_id + channel_id; one channel may bind several verified page/site IDs; provider account ownership proof, capabilities, hours, routes and scoped secret references |
| bot_configs | tenant_id + config_revision, approved persona/intent/workflow/corpus IDs and typed limits; immutable releases |
| products | tenant_id + product_id, category, approved aliases/specs, variants/units, price-rule revision, optional stock snapshot/freshness, licensed image refs (source target1–10), safe links/discount rules |
| services | tenant_id + service_id, scope/exclusions, required intake fields, duration/availability source, fee/deposit rule and version; not forced into product stock semantics |
| faqs / knowledge_base | tenant_id + document_id + version + passage_id, authority/publication scope/effective dates/hash/revocation |
| customers | tenant_id + customer_id, verified identity reference, consent scope; no global cross-business person matching |
| conversations / messages | Both require non-null tenant_id; conversation_id + owner/session/channel/page; messages additionally message_id + sequence + provider event ID + authority/config revision. Composite foreign key `(tenant_id, conversation_id)` prevents foreign-parent assignment |
| orders / appointments | tenant_id + id, owning customer, authorized business command/reference and state; only trusted transaction service can commit; absent from first MVP runtime |
| leads / tickets | tenant_id + id, owner scope, consent revision/digest/expiry, bounded fields/status and scoped staff routing; restricted access and deletion |
| staffs | tenant_id + staff membership ID + external identity + role/expiry; platform-role assignments are separate from tenant roles |
| audit / outbox / tombstones | Explicit tenant scope for tenant-owned events; event/replay ID, payload hash, release and sequence, lease/ack metadata, minimal security facts; tombstones survive restore |

**Source inconsistency resolved explicitly:** the derived brief says the §5 sample `messages` omits tenant_id although the global rule requires it. The future contract requires non-null tenant_id on messages and every tenant-owned record, composite tenant-qualified relationships, ACL before access, and separate tenant DB roles/stores. A join or row filter alone is insufficient. PostgreSQL18 is the proposed pilot physical engine; the table names above are logical requirements, not implemented SQL. Existing SQLite two-table adapter does not implement this domain model or production isolation.

## 3. Channel/page authority and adapter boundary

Every inbound route first verifies provider signature or website session/CSRF authority, request age/replay rules and registered channel/page ownership. Only then resolve **tenant_id + channel_id + page_id** from server-owned mappings. A client tenant, site/page ID, phone number or provider sender string alone grants no identity or private-data access. Website origins are supplemental checks, not signatures. For anonymous website public questions, a server-issued site-bound session grants only public approved knowledge. Later external webhook sender identity remains channel-scoped and must not be merged into a customer identity without verification.

Conceptual adapter input: verified provider account/page, opaque event/message ID, sender/channel-scoped identity, event time, bounded content kind and normalized payload; verification result is constructed by the trusted ingress, never by request JSON. Output: tenant/channel/page bound receipt, server sequence and safe status. Persist ingress event + dedupe record before acknowledging acceptance; if persistence fails return safe failure so a provider can retry. Source target **ack <2s** concerns durable acceptance, not answer completion. Queue worker reauthorizes tenant/consent/config on consumption, then processes async.

Outbound adapter accepts only server-authored commands with tenant/channel/page, target scope, idempotency key, payload hash, policy/consent revision and deadline. Resolve scoped credentials server-side, apply provider-supported signing/authentication and callbacks; authenticate internal dispatch too. If a provider has no signature/idempotency feature, document the weaker guarantee and reconcile delivery receipts; never invent universal exactly-once semantics. No automatic follow of arbitrary URLs/attachments. Cap queues, dedupe TTL against provider redelivery horizon, reject changed-payload duplicate IDs, bound retries with backoff/jitter and dead-letter/manual reconciliation.

Failure model: duplicate/out-of-order callbacks, timeout before/after remote acceptance, process crash around commit/send/ack, temporary queue/database unavailability, expired consent and revoked channel. At-least-once delivery can be deduplicated locally; ambiguous remote sends must pause/reconcile before retrying a transaction. Source **3 retries**, **100 webhook req/min/tenant**, **1,000 dashboard req/min** are candidates, not commitments. Select <=3 retries only for safe/idempotent operations within absolute deadlines and cost allowance; never retry ambiguous non-idempotent business actions blindly. Rate quotas combine tenant, channel, principal, endpoint and global cost; overload must not leak foreign state. Any proposed number is frozen/tested at the relevant gate before use.

Capabilities are declarative: text, image, video, file, buttons, quick replies, carousel, location, delivery/seen events. First MVP supports text website only; unsupported media produces a clear limitation and consented staff option. Later Vision or staff fallback needs separate rights, content size/type checks, sandboxing, malware/SSRF controls and PII approval. Facebook, Zalo OA, Instagram, TikTok and WhatsApp adapters remain design-only and independently gated. Source Facebook-first rollout is **deliberately changed by Owner to NHD Website Widget first**, reducing initial account/webhook/provider-policy dependencies; no claim that all channels work.

## 4. Configurable conversation and industry templates

Proposed generic stages (engineering normalization, not the unavailable source's exact labels): new → identify need → collect missing slots → offer authorized information → confirm intent → draft/authorized-action request → handoff or close. Explicit interrupted/suspended/human-owned/error states. Each transition has allowed actor, guard, consent/rule revision, idempotency and safe output. Model may propose intent/slot updates; trusted code validates and persists state.

Order-related slots include product/variant/specification/unit/quantity; address/payment are not collected in the first MVP. Appointment slots include service/duration/preferred time/timezone, with availability independently checked by an authorized later adapter. Quote slots are not silently converted to order/appointment consent. Store typed slots with source (customer vs approved catalog), confirmation and validity; do not ask a still-valid confirmed slot twice. Invalidate stale price/availability or changed intent explicitly.

Topic A→B→A: maintain a bounded stack of domain-specific topic IDs and typed slots under tenant+customer/session+channel ownership. Switching topic does not overwrite A; returning restores A's confirmed nonexpired slots and revalidates authority/price/config. No reloading another customer's topic by guessed ID. Proposed source policies: max50 context messages, merge5 messages/3s, reminder after30min inactivity, close after24h. These remain configurable candidates; model token bounds take precedence over message count. Merge cannot swallow cancel/withdraw/takeover commands or reorder authority events. MVP sends no proactive idle reminder; closure is silent and cannot renew consent. Any reminder requires later opt-in/channel policy and no assumption of response coverage.

| Template | Common contracts with distinct domain guards | First implementation / future scope |
| --- | --- | --- |
| Fast sale | Product+variant+quantity; authoritative price/stock and explicit order approval; no model commits | Future business phase; no checkout now |
| Consultative sale | Need/spec clarification, compare at most2 approved candidates with reasons, exclusions and available authorized price; no unverified suitability claim | Small NHD consultation→draft quote→handoff first; images deferred |
| Appointment | Service scope, duration, timezone, availability hold, customer confirmation, authorized booking/deposit/cancel policy | Later HANU/ZENA or other tenant config, no calendar/API now |
| B2B quote | Specification, quantity, delivery terms and validity; staff approval before binding offer; no invented discounts/lead time | NHD single-line nonbinding draft first; multi-line/negotiation later |

No template assumes HANU/ZENA operate in any particular way; tenant business approver chooses permitted service rules later. Proposed eight objection playbook slots and their exact source classes are not enumerated in the public brief, so their names remain UNKNOWN. Future tenant-approved playbooks must ground each response in policy; complaints always offer staff, never invent refunds. Upsell source target is at most1 and stop on refusal; MVP disables it. Later lead statuses are proposed `new/qualified/consented/assigned/closed/withdrawn`, requiring business review, not claimed source vocabulary. Remarketing24h/3d/7d and feedback24h are deferred, revocable opt-in outbound actions with quiet hours/provider rules, never automatic consent from an inquiry.

Handoff triggers: ask-human/complaint immediately; proposed two failed attempts or configured high-value threshold also offer staff without automatically exporting context. Threshold/value classification is tenant business policy, not invented NHD pricing. Human takeover uses authenticated staff membership and a control epoch, cancels queued generation and suppresses late bot outputs. Staff return is a separate authorized ordered event; fresh bot work resumes only after context/consent/source revalidation. Session expiry or withdrawal wins over a stale return event. Full live stop/return proof needs real staff and inbox integration later.

## 5. Onboarding a second tenant without editing core

1. Platform admin provisions inactive tenant identity, separate worker/store roles, queue namespace and secret scope; verifies no cross-tenant grants. Tenant admin/staff identities receive least-privilege memberships.
2. Business approver supplies authorized product **or service** records, FAQs/policies, persona and approved template selection in schema-versioned data; validate and approve exact corpus/config hashes. No copied NHD rules or price defaults.
3. Verify channel provider-account/page ownership (or approved site/domain), map tenant/channel/page, capabilities, hours and staff routes. Secrets are scoped references, not included in config export.
4. Run schema/authorization/oracle tests, all six relevant E2Es, same-name different-price cases, failure/replay/recovery/deletion and rollback. No tenant becomes active on an incomplete gate.
5. Activate config/data atomically under the separately approved rollout; smoke-test with synthetic identities, monitor quota/routing, keep rollback to inactive or prior authorized revision. Record actor, time, test/manifest hashes and actual onboarding elapsed time.

Design test: with an unchanged core artifact hash, load a second **synthetic service tenant** config and approved sources; distinguish unit/fee/duration from NHD product quantity, reject cross-tenant credentials, and demonstrate independent rollback. No second live tenant is onboarded now. Source target **<30 minutes** excludes unresolved contracts/data preparation only if the measurement protocol explicitly says so; report both technical activation time and full business onboarding elapsed time. Target remains NOT_RUN and must not conceal prework.

Developer handover checklist: approved RTM/ADR; exact artifacts/dependency SBOM/licensing/advisories; config/data schemas and example synthetic exports; secret/role inventory; API/channel version contracts; frozen oracles and result manifests; source promotion/rollback; recovery/deletion/backup runbooks; spend limits and monitoring; operator training/coverage; incident owner and kill switch; declared known gaps; independently accepted release SHA. No transfer of private data through this public repo.

## 6. ADR-002 retention and privacy interpretation

Source inputs **30-day raw webhook payload** and **90-day trace** conflict with no plaintext personal details in logs. Proposed revision: do not retain raw webhook bodies by default after verified normalization; use bounded transient memory only and never general application logging. Store minimal event ID/signature-validation outcome/payload digest and replay metadata in restricted tenant audit. If diagnostics genuinely need payloads, request a separate lawful, explicit short retention exception, redaction/encryption/access controls and deletion plan first. Hashes of low-entropy PII are not anonymization.

Proposed pilot schedule: conversation/handoff content7 days; normalized security/audit metadata30 days; encrypted backups30 days with tombstones applied before restore; session idle24h/hard7 days bounded by consent and channel policy. These are engineering defaults pending privacy/legal/business approval. Original90-day trace target is **revised/deferred**, not silently fulfilled by30 days. Later90-day security retention must justify its minimal fields and lawful basis; conversation and marketing consent remain separate. Deletion request first blocks serving and cancels jobs, then purges content/derived indexes; retained legally required audit uses minimum fields, restricted purposes and no retrieval for replies. Provider retention and contractual exceptions are separate from local TTLs; `store:false` does not promise immediate provider deletion.

Withdrawal cancels unsent work and suppresses late outputs or subsequent sharing. It cannot retract bytes already sent or records already held by a provider. Confirm allowed fields, processing terms, retention and provider deletion/reconciliation before approving any real-data path. A local tombstone records the revocation and blocks replay after restore.
