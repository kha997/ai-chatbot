## Proposed single-run budget

Start with one model, one sequence, **2,048 context tokens** and **128 output tokens**. Apply the context at the Ollama server and mirror it in OpenCode. FP16 KV payload for this model is `40 layers × 8 KV heads × 128 head dimensions × 2 (K and V) × 2 bytes`, or **160 KiB per token** and **320 MiB at 2,048**. Weights plus KV alone are about 9 GiB. Graph, allocator and compute buffers are additional. A preliminary GPU estimate is **10–12 GiB VRAM**; request at least **12 GiB free VRAM** at preflight in an Owner-coordinated exclusive window and abort if headroom or exclusivity is lost. This is an admission threshold and estimate, with no hard VRAM cap established. [Qwen model configuration](https://huggingface.co/Qwen/Qwen3-14B/raw/main/config.json) · [Ollama context and concurrency](https://docs.ollama.com/faq).

For that GPU path, propose **4 GiB host/WSL memory cap** for the local process group, including a **1 GiB OpenCode allowance**, Ollama host buffers and mapped pages. Require **6 GiB Windows available** first to leave headroom for WSL and the host. Verify enforcement and mapped-file behavior before using these limits. Set CPU quota to at most **four logical CPUs** (400% in a delegated systemd user scope), cap PIDs and require **zero additional swap** for the trial. A CPU-only load would need about **12–15 GiB** including weights, KV, working buffers and OpenCode, with a proposed minimum **16 GiB host headroom**. It is impractical at this snapshot. Neither path was benchmarked. Avoid global `.wslconfig` edits.

## Endpoint and mock proof

- Use a disposable outer network namespace with only loopback and no external route. Bring up loopback under its user namespace capabilities, then drop all capabilities before starting the fixture. OpenCode's minimal Bubblewrap filesystem shares **only that private network namespace** with the approved listener. It sees synthetic read-only input, fresh HOME/XDG state and no mounted host home, drive, GPU or Windows interop.
- In OpenCode **1.18.30**, pin `enabled_providers=["local-ollama"]`, model and small model `local-ollama/qwen3:14b`, and provider base URL `http://127.0.0.1:11435/v1`. Use the installed v1 `provider/options` schema, deny tool permissions, use `--pure`, empty plugin/MCP lists, no credentials, disabled updates/sharing/model fetch and the OS no-egress boundary. The exact installed ELF resolved these flags/config through `debug config`. [OpenCode providers](https://opencode.ai/docs/providers).
- The HTTP fixture admitted one synthetic request in each independent case. It denied unknown paths, wrong model, added tools and replay. It accepted the exact integer oracle `{"catalog":2,"handoff":1,"total":3}`, refused malformed results, and stopped a delayed response on timeout. A synthetic filesystem and external-network probe remained blocked. All fixture sockets closed. **Zero real model POSTs.**
- This establishes configuration resolution and loopback HTTP reachability. The mock HTTP client is Python. OpenCode never ran a generation command. Plugin flags and the cold offline availability of the compatible SDK/provider dependency require their own offline verification before inference. The enforced no-egress boundary does not depend on those flags. **BLOCKED_CLI_ADAPTER** for live use.
- For a separately approved trial, keep Ollama in a second isolated backend network namespace and expose only the one-shot loopback gate to OpenCode. Bridge the namespaces through a private Unix socket, consistent with the existing reviewed isolation pattern. The gate must pin and count physical model requests, including any auxiliary CLI call. Keep one model/runner, mounted project model files only, no-cloud mode, no pulls, hard time/output caps and cleanup of the daemon plus the gate. Verify direct backend access fails. This is a proposed trial topology; only the simpler front-end loopback with a mock was exercised.
